# Scenario overhead benchmark plan

The benchmark measures the public console runner as a developer uses it. An independent harness launches a small workload executable through its CLI, validates its typed JSON response, and records process and operation costs. The harness has no product project references. The workload is an ordinary public-API consumer of Core and Cli, rather than an internal measurement hook.

Hypothesis: structured steps add measurable allocation and execution overhead, especially with listeners enabled. The suite does not assume that overhead is negligible. It compares four deterministic arms: an empty-run process floor, existing delegate cases, one-step scenarios, and five-step scenarios. Every arm runs with listeners off and on. No HTTP server, Docker stack, external dataset, or credentials are involved.

The fixed dataset contains 10,000 cases per non-floor arm. Each process starts cold, performs one workload, and emits a correctness-checked result. The harness rotates arm order deterministically, discards two warmup rounds, and retains twelve paired rounds. It records wall-clock process time, operation elapsed time, allocated bytes measured by `GC.GetTotalAllocatedBytes`, and process peak working set. The operation stopwatch includes CLI formatting to a null writer, result collection, and execution, but excludes descriptor construction and process startup. Memory measurements are process-wide and should not be read as retained bytes per test.

Reports record the source hash, commit, dirty state, dataset/configuration hashes, SDK/runtime, CPU, OS, host, counts, and timestamp. A failed subprocess, incorrect count, missing row, or canceled run is incomplete and cannot be compared. Baselines must be refreshed on a different machine; timing comparisons across hardware are rejected.

The gate requires a regression greater than 20 percent and a paired bootstrap 95 percent interval above zero. Time and peak-memory comparisons also require the candidate p95 to exceed the baseline p95 by 20 percent. The bootstrap uses 2,000 resamples with seed 1729. The 20 percent tolerance is a conservative starting budget for short process-based measurements; review observed noise before tightening it. Baselines and comparison results belong under `benchmarks/`; do not treat these synthetic no-work workloads as application-level performance guarantees.

Status and evidence are tracked in the archived BDD implementation plan and `benchmarks/RESULTS.md`. Future improvements are recorded in `IMPROVEMENTS.md`. CI always builds and validates correctness. The benchmark gate runs on a dedicated self-hosted runner whose baseline matches the recorded environment; shared hosted CI cannot honestly compare against a developer-machine timing baseline.
