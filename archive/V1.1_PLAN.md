# Touchstone v1.1.0 Plan

Status: complete, 2026-11-05. Built on the `feature/v1.1.0` branch and merged into main.

1.1.0 is a minor release. Everything in it is additive: two new `TestRunOptions` properties, one new exception type, three new telemetry names, and two new console runner options. Package validation runs against the published 1.0.0 packages, so a breaking change fails the pack. The defaults are unchanged, so a 1.0 consumer that upgrades gets exactly the 1.0 behavior until it sets one of the new options.

Authorization: the user approved the 1.1.0 version, the `feature/v1.1.0` branch, the merge into main, and publishing the packages to nuget.org with a temporary API key. The key is not recorded anywhere in the repository.

## 3. Design decisions

**Timeouts are cooperative.** When `CaseTimeout` elapses, the case's token is canceled and the engine keeps waiting for the case to return. The alternative was to abandon a case that ignores its token and move on. That would let an abandoned case keep running while the next case starts, deliver sink callbacks after its result was reported, and run scenario cleanup at an unpredictable time. All three break guarantees that 1.0 makes, so they were not acceptable. A case that ignores its token is still reported as timed out once it returns. `CleanupTimeout` already works this way.

**What the timer covers.** The timer starts when the case body (or the scenario's context factory) starts and stops when the body returns (or the last step finishes). Scenario cleanup, suite hooks, and sink callbacks are outside it. Cleanup already has its own budget, and counting it would turn a case whose steps all finished on time into a timeout. An internal `CaseDeadline` records whether the timer fired before the guarded work ended, so work that runs afterwards cannot change the answer.

**Timeout outcome.** A timed-out case is `Failed`, not `Canceled`. `Canceled` means the caller canceled the run, and a timeout is a property of the case. The result's exception is a `CaseTimeoutException`, which derives from `TimeoutException` and carries the test identity and the timeout. When the case observed the token and threw, that exception is the inner exception. A timed-out scenario step is `Failed`, later steps are `NotRun`, and cleanup runs as usual. Caller cancellation wins over a timeout.

**Parallelism stays inside a suite.** Suites still run one after another, and each suite's `beforeSuiteAsync` and `afterSuiteAsync` still bracket all of its cases. Running suites concurrently would make suite hooks overlap, which suites written for 1.0 do not expect. Cases start in declaration order. Results reach the sink in completion order, and sink callbacks are serialized, so sinks written for sequential runs (including `ConsoleResultSink` and `TestResultCollector`) stay correct. With `StopOnFirstFailure` or caller cancellation, cases that have not started are `NotRun` and running cases finish. A sink exception stops new cases from starting, waits for running cases, then escapes the run as it would in a sequential run.

**Default 1 keeps the sequential path.** `MaxDegreeOfParallelism = 1` runs the 1.0 loop unchanged, so the defaults produce exactly the 1.0 behavior, order, and telemetry.

**Adapters.** The xUnit v2, xUnit v3, and MSTest row keys now carry the case timeout, so `CaseTimeout` set on the options passed to the data source applies when each row runs. NUnit rows hold the descriptor, and `TouchstoneNunit.ExecuteAsync` already takes the options. `MaxDegreeOfParallelism` applies to `TestExecutor.RunAsync` and therefore to the run-all base classes and the console runner. One-row-per-case hosts use their framework's own parallelization.

**Console runner.** `--case-timeout <seconds>` (0.001 to 86400) and `--parallel <n>` (1 to 1024).

## 4. Sample host duration

IMPROVEMENTS.md said the MSTest sample host took about 44 seconds against 5 to 8 seconds for the NUnit and xUnit hosts, and suggested looking at `WebApplicationFactory` start-up under MSTest. Measuring showed the process was mostly idle (22 seconds of wall time, 1.5 seconds of CPU) and that the NUnit run-all test was also slow (7 to 13 seconds). The delay was not MSTest-specific.

Each `WebApplicationFactory` host loads `appsettings.json` with reload on change, which watches the content root (the test's `bin` directory) for file changes. On macOS, setting up that watcher stalled host start-up for between 0.05 and 7.3 seconds, varying from run to run. With `hostBuilder:reloadConfigOnChange` set to false, start-up took about one millisecond every time. `SampleApiHost` sets it through `UseSetting`. After the change, every sample host finishes in under 300 ms of test time.
